# 0012 — `v_daily_report` เป็นแหล่งความจริง `v_monthly_report` ต่อยอดจากมัน

- **สถานะ:** ตัดสินใจแล้ว
- **วันที่:** 2026-08-11
- **ต่อจาก:** ADR 0011 (pipe ของรายงาน) · **ปลดข้อค้างของ:** ADR 0011 หัวข้อ "ผลที่ยอมรับ"

## บริบท

หน้า `/report` ต้องให้เจ้าของร้านเลือกช่วงเวลาเองได้ พร้อมปุ่มลัด วัน / เดือน / ปี

`v_monthly_report` bucket ด้วย `date_trunc('month', …)` ทั้ง 4 pipe **ระดับที่ละเอียดกว่าเดือนจึงไม่มีอยู่จริงในสคีมา** และไม่มี view อื่นที่รวมเงินทั้ง 4 ทางไว้ด้วยกัน (`v_sale_profit` ครอบแค่ pipe เดียว)

ข้อเท็จจริงที่ query จากของจริงก่อนตัดสินใจ:

- ทั้ง 4 pipe มีเวลาจริงติดมาหมด — `sales.sold_at`, `repair_jobs.closed_at`, `device_units.financed_at` เป็น `timestamptz`, `expenses.spent_at` เป็น `date` อยู่แล้ว
- **ไม่มี view อื่นใน `public` ที่พึ่ง `v_monthly_report`** — drop แล้วสร้างใหม่ได้โดยไม่ลาก dependency

การ bucket ระดับวันจึงเป็นการ derive ล้วน ไม่ต้องแก้ตาราง ไม่ต้องเพิ่มกติกาเงินใหม่

## การตัดสินใจ

**สร้าง `v_daily_report` ถือ pipe ทั้ง 4 ไว้ที่เดียว แล้วนิยาม `v_monthly_report` ใหม่เป็น `group by date_trunc('month', day)` บนตัวนั้น**

- pipe ยกมาทั้งดุ้นจาก `20260810120000` เปลี่ยนแค่ `date_trunc('month', X)::date` → `X::date`
- gate `pos_is_owner()` อยู่ใน `v_daily_report` ที่เดียว `v_monthly_report` รับสืบมา ไม่เขียนซ้ำ
- `net_profit` บวกข้ามวันได้ตรงๆ เพราะมันเป็นผลรวมเชิงเส้นของคอลัมน์ข้างๆ ไม่ต้องคำนวณใหม่ตอน rollup
- ทั้งสอง view `revoke all from anon, authenticated` แล้ว `grant select` เฉพาะ `authenticated` — default privilege ของ Supabase แจก write ให้ view ที่เพิ่งสร้างเสมอ (รูเดียวกับ `v_pos_topup_carriers` และ `v_pos_repairs`)

การจัดกลุ่ม วัน/เดือน/ปี บนหน้าเว็บทำฝั่ง client จากผลลัพธ์ชุดเดียว ไม่ยิงคนละ endpoint — `day` เป็นสตริง `'YYYY-MM-DD'` ตัดเอา 7 ตัวแรกได้เดือน 4 ตัวแรกได้ปี ไม่ต้องแปลงเป็น `Date` (ซึ่งจะลาก timezone กลับเข้ามา)

## ทางที่ไม่เลือก

**เพิ่ม `v_daily_report` เฉยๆ ไม่แตะ `v_monthly_report`** — ปลอดภัยกว่าในวันนี้ ไม่ต้อง re-verify งาน ADR 0011 ที่เพิ่ง apply ไป แต่ทำให้ pipe logic ราว 60 บรรทัดมีสองชุด กติกาเงินในไฟล์นี้ย้ายมาแล้ว 3 รอบ (ADR 0003 → 0010 → 0011) การย้ายรอบหน้าถ้าลืมแก้ชุดใดชุดหนึ่ง จะได้ตัวเลขสองหน้าจอที่ไม่ตรงกันโดยไม่มีอะไรเตือน — เป็นความพังแบบเงียบ ซึ่งแพงกว่าค่า re-verify หนึ่งรอบ

**ทำ RPC `rpc_report(p_from, p_to)` รับช่วงเวลาแล้วรวมยอดใน SQL** — ย้ายการจัดกลุ่มไปฝั่งฐาน แต่ต้องเขียน grouping logic เพิ่มและกลายเป็นผิวสัมผัสอีกอันที่ต้อง gate เอง ในเมื่อข้อมูลทั้งปีของร้านนี้อยู่ระดับร้อยแถว การส่งวันดิบมารวมฝั่ง client ถูกกว่าทุกทาง

## ผลที่ยอมรับ

- `v_monthly_report` อ่านผ่านชั้น view สองชั้น ช้าลงเชิงทฤษฎี — วัดแล้วไม่มีนัยที่ขนาดข้อมูลระดับนี้ (197 วัน / 9 เดือน)
- ใครแก้กติกาเงินต่อจากนี้ **ต้องแก้ที่ `v_daily_report` เท่านั้น** แก้ที่ `v_monthly_report` ไม่มีผลเพราะมันไม่มี pipe ของตัวเองแล้ว
- pipe 2 (งานซ่อม) และ pipe 3 (SF+) ยืนยันตอน apply ไม่ได้เพราะ prod ยังไม่มีแถวเลยทั้งคู่ — พิสูจน์ผ่าน e2e `report.spec.ts` แทน โดยสร้างงานทิ้งจริงแล้ววัดส่วนต่างของ `repair_profit`
