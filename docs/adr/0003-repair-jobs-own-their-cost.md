# 0003 — งานซ่อมเป็นตารางถาวร และเป็นเจ้าของต้นทุนอะไหล่แต่ผู้เดียว

- **สถานะ:** ตัดสินใจแล้ว
- **วันที่:** 2026-08-05

## บริบท

ระบบเดิมมี `repairQueue` เป็นที่พักชั่วคราว พองานจบก็ลบทิ้งแล้วแปลงเป็นบรรทัดในบิลขาย

หลักฐานว่ามันพัง: ไฟล์ backup มี `auditLogs` บันทึก `รับงานซ่อม` **126 ครั้ง** แต่ `repairQueue` **ว่างเปล่า** ประวัติซ่อมทั้งปีเหลือแค่ข้อความค้นไม่ได้ ตอบไม่ได้ว่าเครื่องนี้เคยซ่อมอะไร หรือเดือนนี้ซ่อมจอกี่งาน

ที่หนักกว่าคือ **ต้นทุนอะไหล่ถูกบันทึกสองที่**:
- เข้า `expenseList` ชื่อ `"ต้นทุนงานซ่อม: แพรชาร์จ Oppo a17"` (108 แถว)
- และเข้าเป็น `cost` ของบรรทัดในบิลขาย

โค้ดเดิมเลยต้องแปะ flag `costAlreadyRecorded: true` บนบรรทัดในบิลเพื่อกันไม่ให้รายงานหักซ้ำ **flag ที่มีไว้กันโครงสร้างของตัวเองคือสัญญาณว่าโครงสร้างผิด ไม่ใช่ฟีเจอร์**

## การตัดสินใจ

`repair_jobs` เป็นตารางถาวร เดินสถานะ `รอซ่อม → กำลังซ่อม → รอรับเครื่อง → รับแล้ว` และมีสถานะปลายทางอีกทางคือ `ลูกค้าทิ้ง`

**ต้นทุนอะไหล่อยู่ที่งานซ่อมที่เดียว** ห้ามปรากฏในตาราง `expenses` — `costAlreadyRecorded` หายไปพร้อมกับกฎพิเศษที่ต้องจำ

### เรื่องวันที่ — ต้นทุนรู้ทีหลัง

เจ้าของร้านยืนยันว่ารู้ราคาอะไหล่ตอนของมาถึง ไม่ใช่วันรับงาน เส้นเวลาจริงมีสามจุดและข้ามเดือนกันได้:

```
1 ส.ค. รับเครื่อง (ยังไม่รู้ต้นทุน)
5 ส.ค. อะไหล่มาถึง จ่ายเงินจริง 180      → part_paid_at
7 ส.ค. ลูกค้ามารับ จ่าย 450               → closed_at
```

เก็บ **สองวันที่เป็นคอลัมน์** (`part_paid_at`, `closed_at`) ทั้งคู่ nullable

**v1 รายงานตามวันปิดงานอย่างเดียว** (กำไรต่องานถูกต้องเสมอ) ไม่สร้างกลไกสลับโหมด — ถ้าวันหลังอยากดูแบบเงินสดเข้า-ออกจริง เขียน query เพิ่มได้ทันทีเพราะข้อมูลมีครบแล้ว ไม่ต้อง migrate ใหม่

### ลูกค้าไม่มารับเครื่อง

สถานะ `ลูกค้าทิ้ง` มีอยู่เพื่อ**ปิดงานให้ได้** ต้นทุนอะไหล่ที่จ่ายไปแล้วตกเป็นค่าใช้จ่ายร้านในวันที่ตัดทิ้ง ไม่ใช่ค้างเป็นงานที่ไม่มีวันปิด ซึ่งจะทำให้กำไรสะสมเพี้ยนขึ้นเรื่อยๆ

## ผลที่ยอมรับ

- ประวัติงานซ่อม 126 งานเดิม**กู้ไม่ได้** ไม่มีชื่อลูกค้า อาการ วันรับ เก็บไว้ตั้งแต่แรก
- ตอน migrate **ไม่นำเข้ารายจ่าย 108 แถวที่เป็นต้นทุนซ่อม** เพราะต้นทุนอยู่ในบรรทัดบิลที่นำเข้าอยู่แล้ว นำเข้าด้วยจะกลายเป็นนับซ้ำแบบเดิม
