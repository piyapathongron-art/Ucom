# 0004 — ตัวเลขเงินที่คำนวณได้ ห้ามเก็บเป็นคอลัมน์

- **สถานะ:** ตัดสินใจแล้ว
- **วันที่:** 2026-08-05

## บริบท

ระบบเดิมเก็บ `profit` เป็นตัวเลขในทุกบิล เช่น `profit: 29.700000000000045` ทั้งที่มันคำนวณจากบรรทัดในบิลได้อยู่แล้ว

ปัญหาของการเก็บ: ถ้าวันหนึ่งตัวเลขในคอลัมน์ไม่ตรงกับผลรวมของบรรทัดจริง **ไม่มีใครรู้ว่าอันไหนถูก** และไม่มีใครรู้ด้วยซ้ำว่ามันไม่ตรง

เรื่องนี้จะเกิดซ้ำกับตัวเลขอีกสองตัวในระบบใหม่ที่ล่อให้เก็บเหมือนกัน — ยอดเครดิต SF คงเหลือ และยอดวอลเล็ตค่ายคงเหลือ

## การตัดสินใจ

ตัวเลขต่อไปนี้**ไม่เก็บเป็นคอลัมน์** ใช้ view หรือคำนวณตอน query:

| ตัวเลข | คำนวณจาก |
|---|---|
| กำไรของบิล | ผลรวมบรรทัด − ส่วนลด |
| ยอดวอลเล็ตค่ายคงเหลือ | เงินที่เติมเข้า − ต้นทุนเติมเงินที่ขายไป |
| ยอดเครดิต SF คงเหลือ | วงเงิน − มูลค่าเครื่องที่ยังไม่เคลียร์ |
| ต้นทุนเติมเงิน | ยอด × (1 − อัตราค่าคอมของค่ายนั้น) |

**สิ่งที่ยังต้องเก็บเป็นคอลัมน์:** ชื่อ/ต้นทุน/ราคาที่ snapshot ไว้ในบรรทัดบิล — อันนั้นไม่ใช่ค่าที่คำนวณได้ มันคือ**ข้อเท็จจริง ณ เวลาหนึ่ง**ที่จะหาไม่ได้อีกถ้าไม่เก็บ (ADR 0001)

**อัตราค่าคอมเติมเงิน 3%** เก็บเป็นแถวในตารางตั้งค่าต่อค่าย ไม่ฝังในโค้ด — ตอนนี้เท่ากันทั้งสามค่าย แต่ถ้าค่ายไหนปรับ ต้องแก้ได้โดยไม่ deploy

## ผลที่ยอมรับ

- query รายงานซับซ้อนกว่าการอ่านคอลัมน์เดียว — ยอมรับได้ ข้อมูลระดับพันแถว Postgres ไม่รู้สึกอะไร
- ถ้าวันหนึ่งข้อมูลโตจนช้าจริง เติม materialized view ทีหลังได้ โดยไม่ต้องแก้โครงสร้างตาราง
