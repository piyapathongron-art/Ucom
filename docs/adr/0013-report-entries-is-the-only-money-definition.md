# 0013 — นิยามเงินอยู่ที่ `v_report_entries` ที่เดียว รายงานที่เหลือ sum ต่อจากมัน

- **สถานะ:** ตัดสินใจแล้ว
- **วันที่:** 2026-08-14
- **ต่อจาก:** [0012](0012-daily-report-view-is-the-source-of-truth.md) (ซึ่งทำให้ `v_daily_report` เป็นตัวตั้ง และ `v_monthly_report` sum ต่อจากมัน)

## บริบท

เจ้าของร้านขอกดดูลึกกว่าตัวเลขสรุป: กดที่ปี/เดือน/วัน แล้วเห็นรายการจริงที่ประกอบกันเป็นตัวเลขนั้น
ลงไปถึงระดับบิลและรายการสินค้าในบิล

ก่อนหน้านี้ `v_daily_report` นิยาม 4 ท่อเงินไว้ในตัวเองเป็น CTE (`pipe`) แล้ว `group by day` ทิ้ง
รายละเอียดไปทั้งหมด รายการดิบจึงไม่มีทางออกมาจาก view นี้ได้เลย

ท่อทั้ง 4 ไม่ได้ตรงไปตรงมา — บิลที่ผูกกับงานซ่อมถูกตัดออกจากยอดขาย · งานซ่อมนับที่ `closed_at`
ไม่ใช่วันที่รับเครื่อง · งานที่ถูกทิ้งเอาเฉพาะค่าอะไหล่ (ADR 0011) · SF+ นับแค่ค่าคอมไม่นับราคาเครื่อง
(ADR 0002)

## ทางเลือก

**ก. ลอกตรรกะ 4 ท่อไปเขียนซ้ำฝั่ง React** — ไม่ต้องแตะฐานข้อมูลเลย แต่นิยามเงินจะมี 2 ชุด
วันที่ใครแก้ชุดหนึ่ง หน้า drill กับตัวเลขสรุปจะไม่ตรงกันแบบเงียบๆ — **ไม่เลือก**

**ข. สร้าง view ใหม่แยกต่างหาก ไม่แตะ `v_daily_report`** — เสี่ยงตอน deploy น้อยที่สุด
แต่ก็ได้นิยาม 2 ชุดเหมือนกัน แค่ย้ายไปอยู่ใน SQL ทั้งคู่ — **ไม่เลือก**

**ค. สร้าง `v_report_entries` (1 แถว = 1 รายการเงิน) แล้วให้ `v_daily_report` sum จากมัน** — **เลือกอันนี้**

## การตัดสินใจ

`v_report_entries` คือที่เดียวที่นิยามว่าอะไรนับเป็นเงินของวันไหน คอลัมน์เงิน 6 ตัวเหมือน
`v_daily_report` เป๊ะ บวกคอลัมน์บอกที่มา: `day`, `occurred_at`, `kind` (`sale`/`repair`/`sf`/`expense`),
`ref_id`, `label`, `detail`

ห่วงโซ่กลายเป็น **`v_report_entries` → `v_daily_report` → `v_monthly_report`** — ตัวเลขที่กดกาง
กับตัวเลขสรุปมาจากนิพจน์เดียวกัน แยกกันไม่ได้แม้จะพยายาม

- gate เดิม `pos_is_owner()` ย้ายมาอยู่ที่ entries (view ชั้นบนได้ผลเดียวกันเพราะอ่านต่อจากมัน)
- `security_invoker = false` + `grant select to authenticated` เท่านั้น ตาม pattern เดิม
- หน้า `/report` กางทีละชั้น ปี→เดือน→วัน โดยไม่ยิงคำขอใหม่ (ตัดจากชุดข้อมูลเดิมในหน่วยความจำ)
  แล้วค่อยยิงหนึ่งคำขอตอนกางวันเป็นรายการ และอีกหนึ่งตอนกางบิลเป็นรายการสินค้า

## ผลที่ยอมรับ

- `v_daily_report` ต้องถูก `create or replace` ทับ — ตรวจด้วย dry-run บน prod
  (`begin … except all ทั้งสองทาง … rollback`) ได้ 198 วันเท่าเดิม ต่างกัน 0 แถว ก่อน apply จริง
- กางวันที่มีบิลเยอะจะได้แถวยาว — ยังไม่ใส่ paging เพราะวันที่ยาวที่สุดในข้อมูลจริงยังไม่ถึงหลักร้อยรายการ
- กางบิลได้เฉพาะรายการ `kind = 'sale'` — งานซ่อมแสดงราคาที่ตกลงกับค่าอะไหล่ในแถวของตัวเองอยู่แล้ว
