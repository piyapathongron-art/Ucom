# 0001 — แยก `products` ออกจาก `device_units`

- **สถานะ:** ตัดสินใจแล้ว
- **วันที่:** 2026-08-05

## บริบท

ระบบเดิมเก็บสินค้าทุกชนิดในตาราง `inventory` เดียว มีคอลัมน์ `qty` กับ `productId`

ข้อมูลจริง 250 แถวฟ้องว่ามันเป็นของสองชนิดที่ถูกยัดรวมกัน:

- โทรศัพท์ 209 แถว ใช้ **IMEI 15 หลัก** เป็น `productId` และ `qty` มีแค่ค่า 0 (180 แถว) หรือ 1 (29 แถว) — ไม่เคยเป็นอย่างอื่น แปลว่า `qty` ไม่ได้แปลว่า "จำนวน" แต่แปลว่า "ขายไปหรือยัง"
- อุปกรณ์เสริม/ซิม 41 แถว ใช้รหัสร้านตั้งเอง (`"0000011"`) และ `qty` เป็นจำนวนจริง (สูงสุด 193)

ผลที่ตามมาในระบบเดิม:
- แถวเครื่องที่ขายไปแล้ว 180 แถวนอนปนอยู่กับของที่ยังมี ต้องกรองทุกครั้ง
- ตอบไม่ได้ว่า IMEI นี้ขายบิลไหน เพราะบรรทัดในบิลเก็บ `productId` แค่ 999 จาก 1,573 รายการ
- เครื่องที่ฝากขายถูกเก็บอีกที่หนึ่งในตาราง `partners` โดยไม่มีอะไรผูกกับ `inventory` — เครื่องเดียวกันมีข้อมูลสองที่ ต้องแก้มือทั้งคู่

## ทางเลือกที่ชั่ง

1. **ตารางเดียว + `qty` แบบเดิม** — ย้ายง่ายที่สุด แต่ลากปัญหาทั้งหมดข้างบนมาด้วย
2. **ตารางเดียว + คอลัมน์ `is_serialized`** — ไม่ต้องแยกตาราง แต่ทุก query ต้องแตกสาขาตาม flag อยู่ดี และ constraint บังคับไม่ได้ (IMEI ควร unique เฉพาะแถวที่เป็นเครื่อง)
3. **แยกสองตาราง** ← เลือกอันนี้

## การตัดสินใจ

แยกเป็น `products` (ของนับจำนวน) กับ `device_units` (1 แถว = 1 เครื่อง, IMEI unique)

**ตาราง `partners` ยุบทิ้ง** — การฝากขายไม่ใช่ของคนละชนิด มันคือสถานะของเครื่องหนึ่งเครื่องที่บังเอิญไปอยู่ร้านอื่น เครื่องนั้นเดินสถานะในแถวเดียวตลอดชีวิต

บรรทัดในบิลขายมี FK สองช่องที่เป็น null ได้ (`product_id`, `device_unit_id`) ควบคู่กับ snapshot ของชื่อ/ต้นทุน/ราคา — snapshot ทำหน้าที่ใบเสร็จที่แก้ไม่ได้ FK ทำหน้าที่ตามรอย คนละงานกัน

## ผลที่ยอมรับ

- ตอน migrate ต้องเดาสถานะเครื่อง 209 ตัวจาก `qty` (0 = ขายแล้ว, 1 = ยังอยู่)
- **เครื่องที่ขายไปแล้ว 180 ตัวผูกกลับไปหาบิลไม่ได้** ประวัติช่วงก่อนย้ายเป็นเส้นขาด ยอมรับแล้ว
- โค้ดหน้าจอต้องรวมสองตารางมาแสดงในหน้าสต็อกเดียว — แลกกับการที่ constraint ระดับ database บังคับความถูกต้องได้จริง
