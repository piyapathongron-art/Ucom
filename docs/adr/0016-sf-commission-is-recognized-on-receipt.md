# 0016 — ค่าคอม SF+ รับรู้เมื่อเงินโอนเข้าจริง

## บริบท

ADR 0002 กำหนดถูกแล้วว่าเครื่อง SF+ ที่ลูกค้าผ่อนไม่ใช่ยอดขาย และค่าคอมคือรายได้ของร้านทั้งหมดจากเครื่องนั้น
แต่ implementation เดิมบังคับให้ staff กรอกค่าคอมตอนกดปล่อยผ่อน แล้ว `v_report_entries` นับค่าคอมในวัน
`financed_at` ทันที ซึ่งขัดกับความจริง: ตอนปล่อยผ่อนยังไม่รู้ยอด และ SF โอนเข้าทีละเครื่องในวันหลัง

## ทางเลือก

1. คงกรอกค่าคอมตอนปล่อยผ่อน — ตัวเลขรายงานเร็วกว่าความจริงและบังคับให้เดายอด จึงไม่เลือก
2. เก็บ `commission` และ `commission_received_at` บน `device_units` — พอสำหรับกรอกต่อเครื่อง แต่การแก้ไขจะทับข้อมูลเดิม
   จนไม่รู้ว่าใครแก้อะไร
3. เก็บ `Commission Receipt` แบบ append-only หนึ่งรายการต่อเครื่อง — เลือก

## การตัดสินใจ

คง `device_units.status = 'financed'` และ `financed_at` เป็นข้อเท็จจริงว่าเครื่องถูกปล่อยผ่อนแล้ว
ส่วนค่าคอมเป็น `Commission Receipt` แยก: หนึ่งรายการที่ยังไม่ถูกยกเลิกต่อหนึ่งเครื่อง มีจำนวนเงิน (รับ `0` ได้)
วันที่เงินเข้า ผู้บันทึก และเวลาเก็บข้อมูล

- เครื่องที่ `financed` แต่ไม่มี receipt ที่ยังใช้งานอยู่ = **รอค่าคอม**
- `0` คือ receipt ที่ยืนยันแล้วว่าไม่มีค่าคอม ไม่ใช่สถานะรอ
- staff และ owner อ่านรายการและบันทึก receipt ได้ โดย staff เลือกวันเงินเข้าย้อนหลังหรือวันนี้ได้ แต่ห้ามวันอนาคต
- owner เท่านั้นที่แก้ไข: ระบบยกเลิก receipt เดิมพร้อมเหตุผล แล้วสร้าง receipt ใหม่ใน transaction เดียว
  รายงานใช้ receipt ที่ยังใช้งานอยู่ จึงสะท้อนข้อมูลที่ถูกต้องล่าสุด ขณะที่ประวัติยังอยู่ตรวจสอบได้
- `v_report_entries` รับรู้เฉพาะ receipt ที่ยังใช้งานและยอดมากกว่า `0` โดย bucket ด้วยวันเงินเข้า
  ไม่ใช่ `financed_at`; `v_daily_report` และ `/report` sum ต่อจาก view เดิมตาม ADR 0013
- `/sf-commissions` เป็นหน้าร่วมของ staff/owner สำหรับรายการรอและรายการที่บันทึกแล้ว นี่เป็นข้อยกเว้นแคบต่อ
  ADR 0006: staff เห็นค่าคอม SF ในหน้านี้เพื่อบันทึกเงินโอน แต่ยังเข้า `/report` และต้นทุนไม่ได้
- `v_close_day_sf` คงอิง `financed_at` และไม่แสดงค่าคอม เพราะนับเครื่องที่ปล่อยในวันนั้น ไม่ใช่รายได้เงินโอน
  ตาม ADR 0014

## ผลที่ยอมรับ

- การแก้ receipt อาจทำให้รายงานวันเก่าขยับเพื่อสะท้อนวันที่และยอดที่ถูกต้องล่าสุด; ประวัติการยกเลิกคือหลักฐานว่าเหตุใดจึงเปลี่ยน
- ไม่สร้าง batch/เลขอ้างอิงการโอน เพราะเจ้าของร้านยืนยันว่า SF โอนแยกต่อเครื่อง
- ก่อน migration ต้องตรวจ production จริง: หากพบ `financed` เดิมที่มีค่าคอมอยู่แล้ว ห้ามเดาวันรับเงินเพื่อ backfill
  และต้องขอคำสั่งเจ้าของร้านเป็นรายข้อมูล
