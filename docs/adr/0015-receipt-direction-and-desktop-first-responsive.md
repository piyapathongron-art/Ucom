# 0015 — ดีไซน์ยึดภาษา "ใบเสร็จ" · สีสงวนไว้ให้สถานะที่ต้องลงมือ · มือถือคือหน้าจออ่าน ไม่ใช่หน้าจอขาย

> **หมายเหตุ (2026-08-16):** กติกา "ไม่มีสี accent" ในเอกสารนี้ถูกแทนที่โดย
> [ADR 0018](0018-uxui-redesign-v2-direction.md) หลังเจ้าของร้านดูของจริงแล้วไม่ถูกใจ — ส่วนที่เหลือ
> (ฟอนต์, mono tabular, breakpoint `md` เดียว, ไม่มี dark mode) ADR 0018 ยังใช้ต่อ ไม่ได้ล้มทั้งฉบับ

## บริบท

เว็บนี้ไม่เคยถูกออกแบบ — มันถูก**ประกอบ**ขึ้นมาทีละหน้าโดยไม่มีระบบกลาง ตรวจของจริงพบว่า:

- ทั้งแอปใช้คลาส responsive ของ Tailwind รวมกัน **5 จุด** ใน 9 หน้า (`grid-cols-2 md:grid-cols-4`
  แบบเดียวกันซ้ำๆ) — พูดได้ว่าแทบไม่มี responsive อยู่เลย
- `layout.tsx` โหลด Geist ด้วย `subsets: ["latin"]` (**ไม่มีอักษรไทย**) แล้ว `globals.css`
  override ทั้ง body ด้วย `font-family: Arial, Helvetica` → **ตัวอักษรไทยทุกตัวเรนเดอร์ด้วย
  fallback ของ OS ที่ไม่มีใครเลือก** และ `--font-sans` ที่ประกาศใน `@theme` ไม่ถูกใช้จริงสักที่
- มี `@media (prefers-color-scheme: dark)` กำหนด token ไว้ แต่ทุกหน้า hardcode `bg-white`
  `text-neutral-900` ทับหมด → dark mode ใช้ไม่ได้จริง เป็นโค้ดตายที่หลอกคนอ่านว่ามันทำงาน
- สีทั้งแอปคือ `neutral-*` ล้วน ไม่มีความหมายเชิงสถานะ ไม่มีเอกลักษณ์

โจทย์คือทำใหม่ทั้งหมดให้รองรับมือถือ/แท็บเล็ต โดยยัง desktop-first

**ข้อเท็จจริงที่กำหนดคำตอบ:** เจ้าของร้านยืนยันว่ามือถือมีไว้**เช็คสต็อก/ดูรายงานตอนไม่อยู่ร้าน**
ไม่ใช่ใช้แทนจอหลักที่เคาน์เตอร์ — งานขายหน้าร้านเกิดบนเดสก์ท็อป/แท็บเล็ตเสมอ

## ทางเลือก

### ทิศทางภาพ

1. **"ใบเสร็จ"** — ยึดภาษาของสิ่งที่ POS ผลิตออกมาเอง ตัวเลขเงิน monospace แบบ tabular
   เส้นคั่นบาง ความหนาแน่นสูง
2. **"แผงหน้าร้าน"** — บล็อกสีแบบป้ายร้านไทย แต่ละโดเมนมีสีของตัวเอง
3. **"โต๊ะช่าง"** — สงบ แม่นยำ สีสงวนไว้เฉพาะสถานะที่ต้องลงมือ

### ขอบเขตมือถือของ `/pos`

1. เดสก์ท็อป + แท็บเล็ต · มือถือขึ้นข้อความบอกให้ใช้จอกว้าง
2. ย่อลงมือถือแบบคอลัมน์เดียว ใช้ได้แต่อึดอัด
3. ทำ POS สำหรับมือถือเต็มรูปแบบ

## การตัดสินใจ

**เลือกทิศทาง 1 เป็นฐาน + ยืมวินัยเรื่องสีจากทิศทาง 3** และ **เลือกขอบเขตมือถือแบบ 1**

สองเรื่องนี้อยู่ ADR เดียวกันเพราะมันค้ำกัน: ความหนาแน่นแบบใบเสร็จ**เป็นไปได้ก็ต่อเมื่อ**
หน้าที่หนาแน่นที่สุด (`/pos`) ไม่ต้องลงจอ 375px

### จานสี — สีมีความหมาย ไม่ใช่มีไว้ตกแต่ง

จงใจ**ไม่ใช้ครีม/เบจ** ที่เป็นค่า default ของงานออกแบบยุคนี้ · ความเป็นกระดาษใบเสร็จมาจาก
**เส้นคั่นกับตัวอักษร ไม่ใช่สีพื้น** · หมึกไม่ใช่ดำสนิทแต่เป็นดำอมน้ำเงินแบบเครื่องพิมพ์ความร้อนจริง

| บทบาท | ค่า |
|---|---|
| พื้นหน้า | `#FBFBFD` |
| พื้นยก (การ์ด/ตาราง) | `#FFFFFF` |
| เส้นคั่น | `#E4E4EA` |
| หมึกจาง | `#6B6F80` |
| หมึก | `#14161F` |
| เตือน (คิวค้าง · SF ใกล้ครบกำหนด) | `#A85B00` |
| ผิดพลาด/ขาด (เงินสดขาด · error · ลบ) | `#B42318` |
| สำเร็จ (ตรงพอดี · บันทึกแล้ว) | `#05704A` |

**ไม่มีสี accent สำหรับตัวเลขสำคัญ** — ยอดที่ต้องเด่น (เช่น "ยอดที่ต้องส่ง") เด่นด้วย**ขนาด
น้ำหนักตัวอักษร และเส้นคั่น** ไม่ใช่สี · เหตุผล: ถ้าให้สีกับทั้ง "สำคัญ" และ "ต้องลงมือ"
สีจะเลิกมีความหมาย แล้วสามสีสถานะข้างบนก็ไร้ผล

### ตัวอักษร

**IBM Plex Sans Thai + IBM Plex Mono** — ตระกูลเดียวกัน ออกแบบมาให้เดินคู่กัน รองรับไทยเต็ม
และมี tabular figures จริง

**เงินและจำนวนที่อยู่ในตาราง/การ์ดสรุปใช้ mono แบบ tabular** · วันเวลาและตัวเลขในประโยคใช้ sans
(บังคับ mono ทั้งแอปทำให้วันที่ดูแปลกโดยไม่ได้ประโยชน์)

### Responsive

- ใช้ breakpoint ค่า default ของ Tailwind · **`md` (768px) เป็นเส้นตัดเดียวที่มีความหมาย**:
  ต่ำกว่า = การ์ด, ตั้งแต่ md ขึ้นไป = ตาราง
- **ตารางบนจอแคบ**: `/stock` `/repairs` `/close-day` `/expenses` แปลงแถวเป็นการ์ด (1 แถว = 1 สิ่งของ) ·
  `/report` ซ่อนคอลัมน์รอง + scroll แนวนอน เพราะเป็นเมทริกซ์ที่ต้องเทียบกันเป็นแถว
  การแตกเป็นการ์ดจะทำลายการเทียบ
- **nav บนมือถือ**: ปุ่มแฮมเบอร์เกอร์เปิด drawer (รับ 8 ลิงก์ได้ และตรงกับความจริงว่ามือถือคือ
  การใช้งานรอง) · `/pos` ใน drawer แสดงแบบจางพร้อมข้อความ "ใช้จอกว้าง" ไม่หลอกให้กดเข้าไปเจอหน้าแจ้งเตือน

### Dark mode — ถอดทิ้ง

ลบ `@media (prefers-color-scheme: dark)` และ token ที่ไม่ถูกใช้ออก · ร้านอยู่ใต้ไฟฟลูออเรสเซนต์
ไม่มีใครขอ และมันเพิ่มพื้นที่ที่ต้องออกแบบและทดสอบเป็นสองเท่า · **โค้ดตายอันตรายกว่าไม่มี
เพราะคนอ่านคิดว่ามันทำงาน**

## ผลที่ยอมรับ

- **`/pos` บนมือถือใช้ไม่ได้โดยตั้งใจ** — ถ้าวันหนึ่งเจ้าของร้านเปลี่ยนวิธีทำงาน (ขายผ่านมือถือจริง)
  ต้องกลับมาแก้ ADR นี้ก่อน ไม่ใช่ค่อยๆ ย่อ UI ไปเรื่อยๆ จนอ่านไม่ออกทั้งสองจอ
- ความหนาแน่นแบบใบเสร็จอ่านยากกว่าบนจอเล็ก — จึงยอมแลกด้วยการแปลงเป็นการ์ดต่ำกว่า `md`
  ซึ่งแปลว่า**หลายหน้าต้องเขียน markup สองชุด** (ตาราง + การ์ด) ต้นทุนนี้รับไว้โดยรู้ตัว
- เลือก mono สำหรับตัวเลขแปลว่า**ต้องเช็คว่าอักษรไทยกับตัวเลข mono วางคู่กันแล้วไม่ขัดตาจริง**
  ก่อนไล่ทำครบทุกหน้า — ถ้าขัด ต้องกลับมาที่ ADR นี้
- ไม่มี dark mode = ผู้ใช้ที่เปิดเว็บกลางคืนเจอจอขาว รับได้สำหรับเครื่องมือหน้าร้าน
