# 0006 — ใช้ Supabase Auth แต่ให้คนใช้พิมพ์ username เหมือนเดิม

- **สถานะ:** ตัดสินใจแล้ว
- **วันที่:** 2026-08-05

## บริบท

ระบบเดิมเก็บรหัสผ่านเป็น **plaintext** ในตาราง `users` — ทั้งสองบัญชีใช้ `1234` และค่านั้นอยู่ในไฟล์ backup ที่เปิดอ่านได้ ใครได้ไฟล์ไปก็ล็อกอินเป็นเจ้าของร้านได้ทันที

สิทธิ์เดิมให้ staff เกือบทั้งหมด (`pos, services, report, installments, stock, settings`) แปลว่าพนักงานเห็นต้นทุนทุกชิ้น กำไรทุกบิล และแก้ตั้งค่าได้

## การตัดสินใจ

ใช้ **Supabase Auth** แต่แปลง username เป็นอีเมลภายในให้อัตโนมัติ (`staff` → `staff@ucom.local`) — ได้ hash, session, refresh token, การหมดอายุ และ `auth.uid()` ที่ RLS ใช้ได้ตรงๆ โดยไม่ต้องเขียนเอง ส่วนคนใช้ยังพิมพ์ `admin` / `staff` เหมือนเดิม

ทางเลือกที่ตกไป: เขียนตาราง `users` + hash เอง (ต้องเขียน session/token เองซึ่งพลาดแล้วเจ็บ) และการบังคับใช้อีเมลจริง (พนักงานไม่มี และพิมพ์ยาวทุกวัน)

### สิทธิ์

| | เจ้าของ | พนักงาน |
|---|---|---|
| ขายของ / รับงานซ่อม / เพิ่มสินค้า | ✅ | ✅ |
| เห็นต้นทุนและกำไร | ✅ | ❌ เห็นแต่ราคาขาย |
| รายงาน | ✅ | ❌ |
| SF+ เครดิต ค่าคอม | ✅ | ❌ |
| ลบ/แก้บิลย้อนหลัง | ✅ | ❌ |
| ตั้งค่า / จัดการผู้ใช้ | ✅ | ❌ |

**บังคับที่ RLS ใน database ไม่ใช่ที่การซ่อนปุ่ม** — ซ่อนแต่ UI แล้วเปิด devtools ก็เห็นต้นทุนหมด การซ่อนคอลัมน์ต้นทุนต้องทำผ่าน view ที่ staff เข้าถึงได้ แยกจากตารางจริงที่เจ้าของเข้าถึง

## ผลที่ยอมรับ

- รหัสผ่านต้องยาวขั้นต่ำ 6 ตัวตามข้อบังคับ Supabase ใช้ `1234` ไม่ได้อีก — เครื่องเคาน์เตอร์ล็อกอินค้างไว้ ไม่ต้องพิมพ์ทุกวัน
- อีเมล `@ucom.local` เป็นอีเมลปลอม **รีเซ็ตรหัสผ่านผ่านอีเมลใช้ไม่ได้** เจ้าของร้านต้องรีเซ็ตให้พนักงานจากหน้าจัดการผู้ใช้แทน
