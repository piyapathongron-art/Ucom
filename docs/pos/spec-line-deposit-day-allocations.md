# LINE deposit day-allocation contract

Date: 2026-10-09. Status: **Implemented; local integration scrutiny PASS. Hosted verification pending.** [ADR 0028](../adr/0028-line-deposit-day-allocations.md) extends [the base API](spec-two-fund-cash-api.md). Amounts are validated exact decimal strings; no floating-point money arithmetic. See [release evidence](release-line-daily-deposits-2026-10-09.md).

## Accounting boundary and storage

Proposed additive storage: an origin record keyed by its original positive pending movement and an append-only allocation journal referencing existing movement sequence, operation UUID, origin ID, handover ID where applicable, and the debit entry being reversed where applicable. Origin includes nullable receiptDay and immutable kind (`receipt`, `opening`, `reconciliation`); positive receipt corrections can create additional origins linked to the same business source/day. Constraints, book lock and journal checks enforce one attribution for each pending movement. Journal entries distinguish available additions/removals, reservation/release and reserved consumption. Journal and cash movements cannot be directly written/read by public, anon or authenticated clients; RPC member/owner authorization remains the boundary.

`ucom_cash_post` and `ucom_cash_finalize_sources` must jointly derive allocation intent from the authorized operation/source; clients cannot inject an arbitrary origin or bypass FIFO through a free-text posting mode. Every pending movement has journal net `availableDelta + reservedDelta = movement.amount`; a reservation/release has net zero and no cash movement. Every origin's available/reserved projection is nonnegative. Sum projections equals pooled balances before returning any command result. Existing `ucom_cash_balances` reserved value remains the sum of bank-bound handover.amount, and must equal the journal reserved projection.

Finalize source receipt allocations only after sale items exist, using final sale net amount. Repair and consignment sale linkage must not create duplicate receipt origins. Pending expense/paid-part/consignment-payout debits consume unreserved origins FIFO; spending reporting dates do not choose the day bucket. Positive reversal of those debits restores exact un-reversed slices (partial reversal FIFO within original debit). Source correction allocation history records net deltas, sourceOperationId and reversal linkage rather than editing prior allocation rows. Own-source available cash is consumed first for a receipt reduction/reclassification, then globally available FIFO; insufficient available cash rolls back the entire correction. A fund switch to pending consumption cannot spend a reservation; a switch away from a pending debit restores its historic slices.

Opening generates one null-day origin for pending > 0. Zero opening has no zero-value origin. Unattributed positive adjustment generates a separate null-day reconciliation origin; negative reconciliation/refund consumes available FIFO. Drawer refunds do not consume pending. Covered sales create no origin. For date semantics and ordering use ADR 0028; no backfill from pre-opening sales.

At first finalization persist immutable receiptDay on the source itself, including transfer receipts with no pending origin. Positive corrections/fund reclassification read this frozen metadata. Extend ucom_cash_guard_source so date-only sales.sold_at/shop_income.received_at updates cannot bypass the transaction guard or change attributed dates; authorized correction does not change receiptDay. Tests must try direct date-only updates, date changes inside correction and transfer-to-cash reclassification after a date-edit attempt. Frozen source dates and existing immutable origin dates must agree.

## Read contract

Extend `rpc_cash_status()` with `dayAllocationsEnabled` and original selected-day metadata on recent handovers. Add member-only `rpc_cash_pending_days(p_version bigint|null, p_after jsonb|null, p_limit integer)` for the complete selectable list independent of recent-history limits. Proposed page limit 1..100; null cursor starts a consistent book-lock read. Return `{epoch, version, asOf, available, reserved, pending, lines, nextCursor}`.

Each line is `{key, receiptDay: YYYY-MM-DD|null, kind: date|opening|reconciliation, available, reserved}`. Known origins on the same day share key `date:YYYY-MM-DD`; unknown origins have stable UUID-based keys and do not merge unrelated reasons. Include outstanding reserved-only lines with available 0 and disable selection. Cursor is opaque, contains the ordered key and version, and is validated against the same epoch/version; a changed version returns refresh-required instead of mixing pages. No recent-100 truncation or silent date omission. The server re-resolves selected lines to origin slices under lock; it never trusts a client day/key to identify arbitrary records. UI may render all pages before selecting; selected-total calculation uses exact amounts.

## Departure command

Member lookup `rpc_cash_operation_snapshot(p_operation_id uuid)` returns the committed result merged with `{operationId,actorId,epoch,action,payload,result}`. `operationId` identifies the command; `id` retains the financial entity ID, which differs for settlement and correction. The original actor can inspect its exact payload; another member can inspect an authorized event snapshot but receives null payload and cannot replay that actor's command. Recovery validates command ID, actor, epoch, action, canonical payload and canonical stored result.

Keep RPC signature `rpc_cash_execute(p_operation_id uuid, p_epoch uuid, p_action text, p_payload jsonb)` and add action `handover_days`:

```json
{"version":42,"lines":[{"key":"date:2026-10-09","amount":"16457"}],"drawerBeforeDeparture":"57","custodian":"F","drawerPhysicallySeparated":true}
```

Require member; active matching epoch; allocation support; primary POS receiving_paused and ack_version = current version; payload.version matches; unique nonempty line keys; each selected amount equals that line's complete current available amount; amounts/description within existing money/custodian validation. Unknown batch keys are equally selectable. Require `0 <= drawerBeforeDeparture < selectedTotal` and physical confirmation; caller must see and accept actual bankBound before cash leaves. The handover ID equals operation UUID. Reuse handover.amount for bankBound, not selectedTotal. Persist original selected lines, precise origin selection and pre-drawer/bank-bound slices. In one transaction: consume pre-drawer selected slices, post pending negative/drawer positive, reserve remaining selected slices, advance version and persist result. The native receiving lock/explicit pause and manual resume protocol remains unchanged. No automatic resume or receipt intake through the phone.

Return base `{id,snapshot}`. Every snapshot includes original metadata `{selectedLines,selectedTotal,drawerBeforeDeparture,bankBound,custodian,reporter}` plus event, eventOperationId, current handover state, asOf/version and drawer/pending/reserved/available balances. Original lines sum selectedTotal, including drawer cash; their label must not claim they all reached the bank.

## Settlement, return and review

Existing action `settle` keeps `{handoverId,bank,drawer,returned,depositedAt,evidencePath,physicallyReturned:true}`. For allocation-aware handovers `drawer` means **additional drawer cash physically returned after departure**, while pre-departure drawer remains a separate immutable field. Require reporter or owner, state handed_over, verified private evidence, valid deposit time, bank > 0, and bank + drawer + returned = handover.amount. In a single transaction consume reserved origin slices bank first, additional drawer second, then release returned pending slices unchanged to original origins. Post pending `-bank-drawer` and drawer `+drawer` once. An internal reserved-consumption path must not rerun ordinary FIFO against unrelated available cash; it is authorized by the locked handover and conserved settlement payload. State reported before final reserved/pending invariant verification, all atomically.

`return` requires reporter/owner, handed_over, reason and full physical return of bankBound; releases precisely the handover's remaining reserved slices, state returned, no pending movement. Original pre-drawer cash remains in drawer. For old handovers without allocation metadata, stop conversion/activation rather than synthesize provenance. Zero-bank outcomes use return, not settle with a fake bank value.

`review` remains owner-only; `evidence` remains reporter/owner after dispute. Neither changes cash or allocations. Reported money is already financially settled; owner confirmation is evidence approval, never the moment to subtract cash again. These event results include the original selected metadata, current review state and immutable balance snapshot. A replacement slip cannot alter the reported deposit amount; incorrect amounts need an explicitly audited correction design, not a hidden edit.

## Replay, concurrency and transport

Keep base authorize-before-replay semantics: same UUID/epoch/action/payload/actor returns the original committed result, different intent rejects. Scope owner-only actions before replay. Members cannot recover another member's operation result by guessing its UUID. Book lock serializes day selection, spending, source correction and reservation. A stale expected version rejects before a new financial effect; it does not quietly reserve fewer days. A committed identical replay remains valid after version advances or receiving resumes. Terminal state prevents a second operation UUID from settling/returning again.

Existing CashForm uses sessionStorage `ucom.cash.operation.v1.*`; PendingCashRequests and hasPendingCashRequests only scan localStorage receipt/request prefixes. This seam does not currently recover deposit intents. Add versioned localStorage `ucom-cash-operation-v2:UUID` records containing `{storageVersion:2,id,actorId,epoch,action,payload,status:"unresolved"}` before financial dispatch. Persist and validate exact prepared payload including evidencePath, never a file blob or signed upload token. A storage failure prevents dispatch. Scanner, recovery UI, ACK/opening gate and new cash-intent gate must include these records, including unreadable/foreign-account entries as blocked investigations. Storage events refresh all tabs; a native creation lock prevents two forms creating parallel replacement intents and a native UUID lock serializes send/retry for that operation. Unsupported lock/storage capability fails closed for new cash intents. Retain receiving intake/pause lock semantics; define a single lock order (receiving lock, then operation creation/UUID lock when both needed) and never acquire receiving lock from inside operation lock.

Recovery verifies current member actor against actorId and calls executeCash with identical UUID/epoch/action/payload, preserving committed snapshot notification. Direct cashExecute alone would skip LINE delivery and is insufficient for cash event recovery. Clear an intent only after validated original-actor success or an authoritative original-intent rejection proving no commit; authentication expiry, foreign actor, payload/UUID mismatch, malformed response and transport failure leave it pending. A successful financial result with LINE failure resolves financial uncertainty and retains committed event notification retry separately. On timeout/unknown response preserve form and block new cash intent until resolved; never move physical cash twice. Known original-intent rejection requires a fresh status/reconfirmation before new UUID. Upload failure leaves handed_over unchanged; an uploaded object is not settlement proof.

Before accepting a new operation, scan current tab's legacy sessionStorage prefix and preserve/import exact legacy id/epoch/action/payload into durable recovery records without new UUID or altered payload. The legacy format omits actorId: mark ownership unresolved unless server-authorized inspection of the existing operation establishes the actor. If no committed operation can be found, do not guess that a possibly in-flight legacy attempt never committed; require original-actor recovery/investigation. Corrupt/conflicting legacy and durable records block new intents and remain intact. Previously closed tabs' lost sessionStorage cannot be recreated; require unresolved legacy physical operations reconciled at cutover and do not claim recovery coverage for lost old data. Test reload, closed-tab restart, another account, expired login, malformed storage, concurrent tabs, old-session import, committed lost response and notification failure.

## LINE command and immutable summaries

Extend webhook event type for message/text, preserving HMAC verification on raw request bytes. Accept exact trimmed `/ฝากเงิน` only from source.type group and configured LINE_GROUP_ID. Reply requires a replyToken and uses trusted application origin fallback already used by push.ts; no request-supplied URL. Wrong group, private chat, unrelated message, missing token or duplicate redelivery cannot mutate cash. Successful reply is navigation only. The destination preserves safe same-origin login return behavior. Do not derive POS membership from LINE sender/display name.

For handover, settlement, return, review, evidence and resend, render from each operation's stored snapshot. Settlement example: title “แจ้งฝากเงิน — รอเจ้าของตรวจ”, reporter/custodian, “เงินที่เลือกจากวันที่” range, every selected daily amount (explicit month/year across boundaries), selectedTotal, drawerBeforeDeparture, bankBound, bank actual, extra drawer return, pending return, current drawer, shop pending and in-custody pending, snapshot timestamp and owner-review button. Null-day lines use explicit labels. Review/dispute summaries use their actual state, never a hardcoded awaiting-review label. Deep link `/cash?handover=UUID` is navigation, not a signed receipt URL or authority; retrieve the authorized specific handover independently of the recent-100 list.

Long selections must not silently omit daily lines or exceed LINE documented payload limits. Split rendering into bounded parts with the same event/snapshot ID and part index; use deterministic retry keys per event/part and the existing LINE retry behavior. Part boundaries never recalculate money. Rendering/checks must verify documented limits before sending; failed send preserves the event snapshot and exposes resend. A resend selects eventOperationId from retained operation results, rather than mutable handover.snapshot. Group summary remains fixed configured destination; web forms do not choose a group.

## Examples and invariants

- Selected A 1,000 + B 500; pre-drawer 57 → A bank-bound 943, B 500, reserve 1,443. Deposit 1,200 and return pending 243 → A consumed, B retains 243. Drawer remains +57; no double posting.
- Same departure canceled → A returns 943, B returns 500; A's 57 stays consumed into drawer. Original selected lines still show A 1,000/B 500 and the event says canceled, not bank deposited.
- A available 1,000/B available 500; reserve all A. Expense pending 200 consumes B, leaving B 300; trying to select A again fails. Cancel reservation restores A 1,000 to availability without minting pending cash.
- Expense consumed A 100/B 50; correct expense down by 120 → restore A 100/B 20, record slice reversals. Later correct down 30 restores only remaining B 30. Each historic debit is restored at most once.
- Receipt A 1,000 already deposited; current B available 500; correct A down 100 → B current available 400, A deposit history unchanged. If B reserved or available <100, reject and require explicit owner reconciliation/physical handling rather than negative cash.
- Opening unknown 57/day A 100; expense 60 → consume unknown 57 then A 3. Queued receipt with original Bangkok day A accepted later creates A allocation only if not covered by physical opening.
- Receipt request crosses Bangkok midnight or transport response is lost → retry identical UUID/payload; persist receipt's original sold_at day, never substitute response day.

For every successful operation assert available + reserved = pending, sum origins equals pending, no negative origin bucket, reservation journal equals handed_over amount sum, selectedTotal equals selected lines, selectedTotal = preDrawer + bankBound, bank + extraDrawer + returned = bankBound, and no extra cash effect on replay/review/resend. Test atomic rollback of all posting/allocation steps on invalid evidence, stale version, missing physical confirmation or authorization failure.
