# plan — เฟส 8 คิว offline

**เป้า:** เน็ตหลุดกลางวัน ขายต่อได้ เน็ตกลับมาบิลขึ้นเอง ไม่มีบิลหาย ไม่มีบิลซ้ำ

**เสร็จเมื่อ:** ปิดเน็ต → ขาย 2 บิล → เปิดเน็ต → บิลทั้งสองโผล่ในฐานข้อมูลด้วย `sold_at` ของเวลาที่ขายจริง และตัวนับบิลค้างกลับเป็น 0

---

## ขอบเขตที่เคาะแล้ว (15 ส.ค. 2026)

| คำถาม | คำตอบ |
|---|---|
| ต้องเปิด/รีเฟรชหน้าตอน offline ได้ไหม | **ไม่ต้อง** — แค่แท็บที่เปิดค้างอยู่ทำงานต่อได้ → **ไม่ทำ service worker** |
| ขอบเขต offline | **ขายอย่างเดียว** — งานซ่อม/SF/รายจ่าย รอเน็ตกลับ |
| บิลที่ส่งแล้ว DB ปฏิเสธ | **ค้างคิวไว้ ขึ้นแถบแดง** ให้คนแก้เอง ห้ามทิ้งอัตโนมัติ |

ที่ตัดสินใจเองระหว่างทาง (R1 — เหตุผลอยู่ในตาราง ไม่ต้องเคาะซ้ำ):

| เรื่อง | เลือก | ทำไม |
|---|---|---|
| `sold_at` | ส่งเวลาที่กดปิดบิลไปกับ payload | `rpc_create_sale` รองรับอยู่แล้ว (`coalesce(payload->>'sold_at', now())`) — ถ้าไม่ส่ง บิลที่ค้างข้ามเที่ยงคืนจะไปโผล่ผิดวัน รายงานรายวันเพี้ยนถาวร |
| ตรวจว่า offline | **ไม่เช็ค `navigator.onLine` ก่อนยิง** — ยิงจริงก่อน ล้มค่อยเข้าคิว | `navigator.onLine` บอกแค่ว่ามี network interface ไม่ได้บอกว่าเน็ตไปถึง Supabase จริง |
| แยก "ส่งไม่ถึง" กับ "DB ปฏิเสธ" | error ที่**มี `code`** = DB ตอบแล้ว → business error โชว์ทันที ไม่เข้าคิว · ไม่มี `code` = ส่งไม่ถึง → เข้าคิว | ถ้าไม่แยก บิลที่ของหมดจริงจะวนอยู่ในคิวตลอดกาล |
| เก็บที่ไหน | `localStorage` | คิวเล็กมาก (บิลละไม่กี่ KB, เน็ตหลุดไม่บ่อย) IndexedDB ไม่คุ้มความซับซ้อน |

## กับดักที่ต้องกันตั้งแต่แรก

1. **key ต้องมีเวอร์ชัน** — `ucom-pos-queue-v1`, `ucom-pos-catalog-v1` เปลี่ยนรูป payload เมื่อไหร่ต้องขึ้นเลข ไม่งั้นคิวเก่า rehydrate แล้วพัง (เคยโดนมาแล้ว)
2. **`client_uuid` ต้องเกิดครั้งเดียวต่อบิล** และเก็บลงคิวไปด้วย — ห้ามสร้างใหม่ตอน sync ไม่งั้น idempotency ของ RPC ไม่ทำงานและลูกค้าโดนตัดเงินสองรอบ
3. **ESLint `react-hooks/set-state-in-effect`** — ห้าม setState ใน useEffect body ใช้ promise chain แล้ว setState ใน `.then()`
4. **Supabase builder ไม่มี `.catch`** — ใช้ `await` ใน try/catch หรือ `.then(onOk, onFail)`
5. **หักสต็อกใน cache ท้องถิ่นตอนขาย offline** — ไม่งั้นรอบ offline เดียวกันขายเครื่องเดิมซ้ำได้ แล้วไปตายตอน sync ทั้งที่กันได้ตั้งแต่หน้าจอ

## รูปของคิว

```ts
type QueuedSale = {
  clientUuid: string;      // = payload.client_uuid, กุญแจกันบิลซ้ำ
  soldAt: string;          // ISO ของเวลาที่กดปิดบิล
  payload: unknown;        // payload ที่จะส่งเข้า rpc_create_sale ทั้งก้อน
  queuedAt: string;
  lastError: string | null; // ข้อความไทยจากรอบ sync ที่ DB ปฏิเสธ
};
```

## ลำดับการทำงาน

**ตอนปิดบิล**
1. ประกอบ payload เหมือนเดิม + `sold_at: new Date().toISOString()`
2. ยิง `rpc_create_sale` → สำเร็จ: เคลียร์ตะกร้า โหลดแคตตาล็อกใหม่ (เหมือนวันนี้)
3. error **มี `code`** → โชว์ข้อความ ไม่เข้าคิว (ของหมดจริง คนขายต้องรู้เดี๋ยวนั้น)
4. error **ไม่มี `code`** (ส่งไม่ถึง) → `enqueue` · เคลียร์ตะกร้า · หักสต็อกในแคชท้องถิ่น · ขึ้นแถบ "บิลค้าง n ใบ"

**ตอน sync** (`window.online` · โหลดหน้า · ปุ่ม · หลังปิดบิลสำเร็จ)
- วนคิวทีละใบตามลำดับที่เข้าคิว (ไม่ `Promise.all` — ลำดับสำคัญกับสต็อก)
- สำเร็จ → ลบออกจากคิว
- error มี `code` → `markFailed` เก็บเหตุผลไว้ **ไม่ลบ** ขึ้นแถบแดง แล้วหยุดรอบนั้น
- error ไม่มี `code` → หยุดรอบ ปล่อยไว้รอบหน้า

## เทส `tests/e2e/offline.spec.ts`

`page.context().setOffline(true/false)` ของ Playwright จำลองได้ตรงเกณฑ์

1. ล็อกอิน staff → ไป `/pos` → รอแคตตาล็อกโหลด
2. `setOffline(true)` → ขาย 2 บิล → assert แถบขึ้น "บิลค้าง 2"
3. `setOffline(false)` → รอตัวนับกลับเป็น 0
4. assert บิลทั้งสองอยู่ใน DB ผ่าน UI (เปิด `/report` ของวันนี้แล้วยอดเพิ่มตามที่ขาย) — ห้าม assert ตัวเลขสัมบูรณ์ ให้วัดส่วนต่างก่อน/หลัง
5. ข้อมูลทุกอย่างที่เทสสร้างใช้ prefix `ZZTEST-` เพื่อให้ `tests/e2e/global-teardown.ts` เก็บกวาดได้
