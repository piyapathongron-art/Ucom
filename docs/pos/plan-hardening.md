# plan — เสริมความแข็งแกร่งหน้าร้าน (Hardening: Offline, Barcode)

**เป้า:** อุดช่องโหว่ความเสี่ยงขายของซ้ำตอน offline, ปลดล็อกบิลเสียที่ติดค้างในคิว, และรับรหัสจากเครื่องสแกนบาร์โค้ดที่หน้าขาย

**เสร็จเมื่อ:** 
1. ปิดเน็ต → ขายเครื่อง IMEI A → รีเฟรชหน้าเว็บตอนยังปิดเน็ต → เครื่อง IMEI A ต้องไม่ปรากฏให้ขายซ้ำในหน้าจอ
2. มีบิล offline ที่ DB ปฏิเสธ → แสดงปุ่มให้พนักงานกดลบทิ้งได้ → หน้า `/close-day` ปลดล็อกให้ปิดร้านได้ปกติ
3. ยิงเครื่องอ่านบาร์โค้ดที่หน้าขาย → สินค้าลงตะกร้าทันทีโดยไม่ต้องคลิกช่องค้นหา

## เฟส 1: ปิดจุดบกพร่องระบบ Offline หน้าร้าน (Offline Queue Hardening)

### 1.1 ป้องกันขายสินค้า/IMEI ซ้ำตอนรีเฟรชขณะ Offline
- **ไฟล์:** `src/app/(staff)/pos/page.tsx` และ `queue.ts`
- **ปัญหาเดิม:** `loadCatalog()` ตอน Offline ดึง Snapshot จาก `readCachedCatalog()` โดยตรง ทำให้สินค้าที่ขายไปแล้วในคิว Offline โผล่กลับมา
- **วิธีแก้:**
  - สร้าง helper function `applyQueueToCatalog(catalogRows, queue)`
  - เมื่อ `loadCatalog()` อ่านแคชมาได้ ให้นำรายการสินค้าที่อยู่ใน `queue` ทุกบิลมาหักลบ:
    - ตัด Device Unit ที่มี `id` อยู่ในคิวทิ้งทันที
    - ลดยอดจำนวน (Qty) ของ Product ตามจำนวนที่ถูกขายในคิว
  - ทำงานครอบคลุมทั้งหน้า Catalog หลัก และแถบสินค้าขายดี (Top Products)

### 1.2 ปลดล็อกบิลที่มีปัญหาออกจากคิว (Queue Deadlock Resolution)
- **ไฟล์:** `src/app/(staff)/pos/QueueBanner.tsx`, `src/app/(staff)/pos/queue.ts`, และ `src/app/(staff)/close-day/page.tsx`
- **ปัญหาเดิม:** บิลที่ DB ปฏิเสธ (`lastError !== null`) จะค้างใน `localStorage` ตลอดไป บล็อกการส่งบิลถัดไป และขวางไม่ให้ปิดร้านใน `/close-day`
- **วิธีแก้:**
  - ใน `QueueBanner.tsx`: ข้างรายการบิลที่ติด `lastError` ให้เพิ่มปุ่ม **"ลบบิลนี้ออกจากคิว"**
  - มีกล่องยืนยัน (Confirm) แสดงรายละเอียดบิลที่กำลังจะลบทิ้ง เพื่อป้องกันการกดพลาด
  - ใน `src/app/(staff)/close-day/page.tsx`: ปรับข้อความเตือนเมื่อพบบิลค้าง หากเป็นบิลที่ DB ปฏิเสธ ให้แสดงปุ่มลัดพาไปหน้า POS หรือมีปุ่มให้กดดู/ลบทิ้งได้ทันที

### 1.3 การทดสอบ (Verification)
- เพิ่ม Test ใน `tests/e2e/offline.spec.ts`:
  1. ทดสอบขายเครื่อง SF/ซื้อขาดตอน offline แล้ว reload หน้าเว็บ → ตรวจสอบว่าเครื่องต้องไม่ปรากฏใน catalog
  2. ทดสอบจำลองบิลเสีย (Database rejection) → ตรวจสอบว่ามีปุ่มกดลบทิ้ง และลบแล้วแถบเตือนสีแดงหายไป คิวกลับมาเป็น 0

## เฟส 2: รับข้อมูลจากเครื่องสแกนบาร์โค้ด (Barcode Input)

### 2.1 ระบบตรวจจับเครื่องสแกนแบบ Keyboard Wedge
- **ไฟล์ใหม่:** `src/app/(staff)/pos/useBarcodeScanner.ts`
- **รายละเอียด:**
  - เครื่องยิงบาร์โค้ด USB/Bluetooth จะส่งข้อมูลแป้นพิมพ์ด้วยความเร็วสูงมาก (< 50ms ต่ออักขระ) และปิดท้ายด้วยปุ่ม `Enter`
  - สร้าง Custom Hook ดักจับ `keydown` ที่ระดับ `window`:
    - หากมีการพิมพ์ต่อเนื่องความเร็วสูงและลงท้ายด้วย `Enter` ให้ถือว่าเป็นข้อมูลจากเครื่องยิงบาร์โค้ด (ไม่ใช่คนพิมพ์)
    - นำรหัสดังกล่าวไปเทียบกับ `code` ใน `v_pos_catalog` (SKU ของสินค้า หรือ IMEI ของเครื่อง) รวมถึงรายการที่อยู่นอกหน้าปัจจุบัน
    - หากพบสินค้าที่ยังขายได้ ให้เพิ่มลงใน Cart โดยใช้กติกาเดิม พร้อมข้อความสถานะสั้น ๆ ที่อ่านได้ด้วย screen reader
    - หากไม่พบหรือสต็อกหมด ให้แจ้งสถานะโดยไม่เพิ่มรายการและไม่สร้างบิล

## กับดักทางเทคนิคที่ต้องระวัง (Known Traps)

1. **ห้ามทำลาย Idempotency ของบิล:** การลบบิลที่ติด Error ในคิว ต้องทำเฉพาะบิลที่ DB ปฏิเสธเด็ดขาดแล้ว (`isDatabaseRejection`) ห้ามเผลอลบบิลที่ค้างเพราะเน็ตหลุดชั่วคราว
2. **โฟกัสของ Scanner:** เวลาพนักงานคลิกโฟกัสอยู่ในช่อง input อื่น (เช่น ช่องพิมพ์หมายเหตุ หรือช่องลดราคา) ข้อมูลสแกนต้องไม่ค้างทับค่าเดิม ตรวจจับชุดตัวอักษรเร็วที่จบด้วย Enter แล้วคืนค่า input เดิมก่อนส่งเข้า Cart
