# Ucom POS — สรุปหน้าจอทั้งหมด (สำหรับทีมออกแบบ UX/UI)

เอกสารนี้สรุปทุกหน้าในระบบ Ucom POS ว่าแต่ละหน้ามีไว้ทำอะไร (จุดประสงค์) ใครใช้ได้ ควรมีฟังก์ชัน/ปุ่มอะไรบ้าง
และมี edge case/behavior พิเศษอะไรที่ควรรู้ก่อนออกแบบใหม่ — สำรวจจากโค้ดจริง ณ วันที่ 15-16 ส.ค. 2569
(อัปเดตล่าสุด 16 ส.ค.: SF+ ตัดวันครบกำหนดออก + เพิ่มราคาขาย)

**เอกสารนี้บอก "มีฟังก์ชัน/ปุ่มอะไรบ้าง" เท่านั้น ไม่ได้กำหนดว่าต้องวางตรงไหน หน้าตาแบบไหน หรือ flow
กี่ขั้นตอน** — ปล่อยให้ทีมออกแบบตัดสินใจเองทั้งหมด ส่วน "edge case/behavior พิเศษ" ที่แนบไว้คือพฤติกรรมที่
ระบบต้องรองรับจริง (เช่น ค่าติดลบได้ ค้นหาไม่เจอ ฯลฯ) ไม่ใช่ข้อบังคับเรื่องดีไซน์

## ภาพรวม role

ระบบมี 2 บทบาท: **staff** (พนักงาน) และ **owner** (เจ้าของร้าน)

| หน้า | Route | staff | owner |
|---|---|---|---|
| เข้าสู่ระบบ | `/login` | ✅ | ✅ |
| หน้าขาย | `/pos` | ✅ | ✅ |
| สต็อก | `/stock` | ✅ | ✅ (เห็นต้นทุนเพิ่ม) |
| งานซ่อม | `/repairs` | ✅ | ✅ |
| ปิดร้าน | `/close-day` | ✅ | ✅ (ดูย้อนหลังได้) |
| ค่าคอม SF+ | `/sf-commissions` | ✅ | ✅ (แก้ไขได้เพิ่ม) |
| รายงาน | `/report` | ❌ | ✅ |
| รายจ่าย | `/expenses` | ❌ | ✅ |
| ตั้งค่า | `/settings` | ❌ | ✅ |

staff เข้าหน้า owner-only ตรงๆ ทาง URL จะถูก redirect กลับ `/pos` อัตโนมัติ

## เข้าสู่ระบบ (`/login`)

**ใครใช้**: ทั้งคู่ (ยังไม่ล็อกอิน)
**จุดประสงค์**: ฟอร์ม username/password ธรรมดา ไม่มี email — ระบบต่อท้าย `@ucom.local` ให้เอง
**edge case**: error message 2 แบบ (กรอกไม่ครบ / ผิด) แสดงเป็น banner สีแดงด้านบนฟอร์ม

## หน้าแรก (`/`)

ไม่มี UI — เป็น redirect เท่านั้น: ยังไม่ล็อกอิน → `/login`, role owner → `/report`, role staff → `/pos`

## หน้าขาย (`/pos`)

**ใครใช้**: staff (owner เข้าได้ ใช้ layout เดียวกัน)
**จุดประสงค์**: หน้าตัดบิลหลักของร้าน ขายสินค้า/เครื่อง/เติมเงิน และปล่อยเครื่อง SF+ แบบผ่อน

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- ค้นหาสินค้า/เครื่องในคลัง เพิ่มเข้าตะกร้าด้วยคลิกเดียว
- "สินค้าขายดี" เป็นปุ่มลัดแยกจากรายการหลัก
- เติมเงินมือถือ 3 ค่าย (True/AIS/Dtac) — เลือกค่าย กรอกยอด เพิ่มเป็นรายการแยก
- เครื่อง SF+ ที่อยู่ในสต็อกมี 2 ปุ่ม: "ขายสด" (เข้าตะกร้าปกติ ร้านจ่ายเงินคืน SF เต็มราคาป้ายทันที ขายให้ลูกค้าตามราคาที่ตั้งไว้) หรือ "ผ่อน SF" (เปิดฟอร์มยืนยันแยก ไม่ผ่านตะกร้า ลูกค้าทำสัญญาผ่อนกับ SF ไม่ต้องกรอกค่าคอมตอนนี้) — เครื่อง SF+ ไม่มีวันครบกำหนดที่บังคับให้เลือกทางใดทางหนึ่ง เลือกได้ทุกเมื่อ
- ตะกร้า: ปรับจำนวนสินค้า (+/-), **แก้ราคาเครื่องได้ก่อนปิดบิล** (ราคาที่ตั้งไว้เป็นค่าเริ่มต้น ต่อรองหน้างานได้), ลบรายการ, ใส่ส่วนลดต่อรายการพร้อมเหตุผล, ส่วนลดท้ายบิลพร้อมเหตุผล, โน้ตท้ายบิล
- เลือกวิธีชำระ (เงินสด/โอน) — โอนต้องกรอกบัญชีที่รับเงิน
- ปิดบิล → คำนวณยอดรวมสด

**ข้อมูลที่แสดง**: การ์ดสินค้า (ชื่อ/รหัส/ราคา/คงเหลือ), รายการในตะกร้าพร้อมยอดรวมแบบ real-time

**edge case/state พิเศษ**:
- **จอแคบกว่า md ใช้งานไม่ได้เลย** — ขึ้นข้อความ "ต้องใช้จอกว้างขึ้น กรุณาเปิดด้วยแท็บเล็ตหรือคอมพิวเตอร์" แทนทั้งหน้า (หน้าเดียวในแอปที่ไม่มี mobile layout เลย ไม่ใช่แค่ซ่อนคอลัมน์)
- **ระบบคิวออฟไลน์**: ถ้าปิดบิลตอนเน็ตหลุด บิลจะถูกเก็บไว้ในเครื่อง (ไม่ขึ้น error ให้ลูกค้ารอ) มี banner เตือนจำนวนบิลค้าง + ปุ่ม "ส่งบิลค้าง" ด้วยมือ, sync อัตโนมัติเมื่อเน็ตกลับมา หรือเปิดหน้าใหม่ บิลที่ยิงไปแล้วโดน server ปฏิเสธจริง (เช่น สต็อกไม่พอ) จะโชว์ error แดงในลิสต์
- ตะกร้าว่างปุ่มปิดบิลถูก disable
- ปุ่ม "ผ่อน SF" มีสถานะ error แยกในฟอร์มตัวเอง ไม่ปนกับ error ปิดบิลหลัก
- ขายสดเครื่อง SF+: ระบบคำนวณต้นทุนให้เองจากราคาป้าย SF ไม่ต้องกรอกเพิ่ม

## สต็อก (`/stock`)

**ใครใช้**: ทั้งคู่ (owner เห็นคอลัมน์ "ต้นทุน" เพิ่มที่ staff ไม่เห็น)
**จุดประสงค์**: จัดการสินค้า/เครื่องในคลัง และบันทึกรับเครื่อง SF+ เข้าใหม่เป็นล็อตจากใบสั่งซื้อ

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- ฟอร์ม "รับเครื่องเข้าจากบิล SF" (พับ/กางได้): กรอกเลขบิล วันสั่ง โน้ต แล้วเพิ่มเครื่องได้หลายแถวในบิลเดียว (IMEI/รุ่น/ราคาป้าย SF/ราคาขาย ต่อแถว, ปุ่ม "+ เพิ่มแถวเครื่อง") — ราคาป้าย SF คือหนี้ที่ร้านต้องจ่ายคืน SF, ราคาขายคือราคาที่ร้านตั้งขายจริง สองค่านี้แยกกันและไม่จำเป็นต้องเท่ากัน (ราคาขายเว้นว่างได้ ถ้าเว้นว่างระบบจะใช้ราคาป้ายแทน)
- ฟอร์มเพิ่มสินค้าเดี่ยว (ชื่อ/SKU/หมวดหมู่/ราคา/จำนวน) และเพิ่มเครื่องซื้อขาดเดี่ยว (IMEI/รุ่น/ราคา) — แยกปุ่มคนละฟอร์ม
- ค้นหาในตาราง
- แก้ไข inline ได้ทุกแถว (ชื่อ/รหัส/หมวดหมู่/ราคา/จำนวน/สถานะ) ปุ่ม "บันทึก" active เฉพาะตอนมีการแก้จริง (dirty state) — เครื่อง SF+ แก้ "ราคา" ในตารางนี้คือแก้ราคาขาย ไม่ใช่ราคาป้าย SF (ราคาป้ายตั้งได้ตอนรับเข้าเท่านั้น)
- เครื่องแก้สถานะได้ (in_stock / consigned_out / written_off)
- **เฉพาะ owner**: เห็น+แก้ "ต้นทุน" แยกปุ่มบันทึกของตัวเอง

**ข้อมูลที่แสดง**: ตารางรวมสินค้า+เครื่องทุกตัว (ชนิด/ชื่อ/รหัส/หมวดหมู่หรือที่มา/ราคา/จำนวน/สถานะ), ลิสต์ "บิล SF ที่ยังมีเครื่องค้าง" (แสดงจำนวนเครื่องที่ยังไม่ปล่อยผ่อน/ยังไม่ขายต่อบิล — ไม่มีวันครบกำหนดหรือการเรียงลำดับตามวัน เพราะ SF ไม่ได้บังคับกำหนดชำระต่อเครื่อง)

**edge case/state พิเศษ**:
- **responsive: table (desktop) ↔ card list (มือถือ)** แยกไฟล์กันชัดเจน
- ฟอร์มรับเครื่อง SF รองรับเพิ่มแถวไม่จำกัด แต่ validate เฉพาะแถวที่กรอก IMEI+รุ่นครบก่อน submit (แถวว่างถูกข้ามไปเงียบๆ)
- คอลัมน์ต้นทุนจะไม่ render เลยถ้าไม่ใช่ owner (ไม่ใช่แค่ disable)

## งานซ่อม (`/repairs`)

**ใครใช้**: staff (owner เข้าได้)
**จุดประสงค์**: รับงานซ่อม ติดตามสถานะ จนถึงปิดงาน/ออกบิล หรือลูกค้าทิ้งเครื่อง

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- ฟอร์มรับงานใหม่ (พับ/กาง): ชื่อลูกค้า, เบอร์, เครื่อง/รุ่น, อาการ, ราคาที่ตกลง, โน้ต
- Filter สถานะแบบ tab: เปิดอยู่ (รอซ่อม/กำลังซ่อม/รอรับเครื่อง) / รับแล้ว / ลูกค้าทิ้ง / ทั้งหมด — ค้นหาชื่อ/เครื่อง/เบอร์คู่กัน
- แต่ละงานมีปุ่มเลื่อนสถานะไปข้างหน้า/ถอยหลังทีละสเต็ป (workflow เชิงเส้น 5 สถานะ: รอซ่อม → กำลังซ่อม → รอรับเครื่อง → รับแล้ว, + ลูกค้าทิ้ง แยกออกไปได้จากสเต็ปกลาง)
- บันทึกต้นทุนอะไหล่แยกต่างหาก (input+ปุ่มบันทึกเฉพาะ), ถ้าบันทึกแล้วโชว์ "กรอกแล้ว" พร้อมวันที่ + ปุ่มแก้ไข
- "ปิดงาน/ออกบิล" เปิด dialog แยก: ราคา, วิธีชำระ (โอนต้องกรอกบัญชี), โน้ต → ยืนยันออกบิลจริง
- "ลูกค้าทิ้ง" ต้องกดยืนยันซ้ำ (2-step confirm) ก่อนเปลี่ยนสถานะจริง

**ข้อมูลที่แสดง**: ตาราง/การ์ด — วันที่รับ, ลูกค้า+เบอร์, เครื่อง+อาการ, ราคาที่ตกลง, สถานะ+ปุ่มเลื่อนสถานะ, ต้นทุนอะไหล่, ปุ่มจัดการ

**edge case/state พิเศษ**:
- **responsive: table (desktop) ↔ card (มือถือ)** เหมือนหน้าสต็อก
- งานที่ "รับแล้ว" (collected) จะไม่โชว์ช่องกรอกต้นทุนอะไหล่/ปุ่มปิดงานอีก (จบ flow แล้ว)
- ปุ่ม "ทิ้งงาน" ต้องมี 2-step confirm ป้องกันกดพลาด ส่วนปุ่มเลื่อนสถานะปกติกดครั้งเดียว

## ปิดร้าน / สรุปรายวัน (`/close-day`)

**ใครใช้**: ทั้งคู่ (owner เท่านั้นที่เปลี่ยนวันที่ดูย้อนหลังได้ — staff เห็นแค่วันนี้)
**จุดประสงค์**: สรุปยอดขายเงินสด/โอนของวันนั้น เทียบกับที่นับได้จริง แล้วบันทึกปิดร้าน

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- (owner) เลือกวันที่ย้อนหลังดูได้ผ่าน date picker
- เพิ่ม/ลบรายจ่ายร้านของวันนั้น (ชื่อ, จำนวน, จ่ายจากเงินสด/โอน) — ลบต้อง confirm
- กรอกเงินสดที่นับได้จริง + โน้ต แล้วกดยืนยันปิดร้าน — ระบบโชว์ส่วนต่างระหว่างที่นับได้กับที่ระบบคำนวณแบบ real-time ขณะพิมพ์ (ตรงพอดี/เกิน/ขาด)

**ข้อมูลที่แสดง**: การ์ดสรุป 4 ใบ (เงินสด/เงินโอน/รายจ่ายเงินสด/ยอดที่ต้องส่ง), จำนวนเครื่อง SF+ ที่ปล่อยวันนั้น, ตารางบิลขาย, ตารางสินค้าขายแยกตามชนิด, ตารางรายจ่าย, สถานะปิดร้าน (ยังไม่ปิด/ปิดแล้วเวลาไหนนับได้เท่าไหร่)

**edge case/state พิเศษ**:
- **บิลค้างคิวออฟไลน์บล็อกการปิดร้าน**: ถ้ามีบิลค้างจากหน้าขาย (เฉพาะวันนี้) จะขึ้น banner เตือนและ **disable ปุ่มยืนยันปิดร้าน** จนกว่าจะ sync
- ถ้าเป็นวันย้อนหลัง (owner ดู) จะไม่มีฟอร์มกรอกอะไรเลย เห็นแต่สรุปอย่างเดียว รวมถึงซ่อนฟอร์มเพิ่มรายจ่าย
- ปิดร้านซ้ำวันเดียวกันได้ (แสดง "ปิดล่าสุดเวลา...")

## ค่าคอม SF+ (`/sf-commissions`)

**ใครใช้**: ทั้งคู่ (owner เห็นปุ่มแก้ไขเพิ่ม, staff ไม่เห็น)
**จุดประสงค์**: บันทึกค่าคอมมิชชั่นของเครื่อง SF+ ที่ปล่อยผ่อนไปแล้ว แยกจากขั้นตอนปล่อยเครื่อง (เพราะตอนปล่อยยังไม่รู้ค่าคอม)

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- ลิสต์ "รอบันทึกค่าคอม": เครื่องที่ปล่อยผ่อนแล้วแต่ยังไม่บันทึกยอด — กดเปิดฟอร์ม inline ต่อแถว กรอกยอด+วันที่รับเงิน (เลือกย้อนหลังได้ ห้ามอนาคต) แล้วบันทึก
- ลิสต์ "ค่าคอมที่ยืนยันแล้ว": ทุก receipt ที่บันทึกแล้ว (รวม 0 บาทด้วย)
- **เฉพาะ owner**: ปุ่ม "แก้ไข" ต่อแถวในลิสต์ยืนยันแล้ว — เปิดฟอร์มแก้ยอด/วันที่ พร้อม**บังคับกรอกเหตุผล**ก่อนบันทึกได้ (เป็นการ void ของเดิม+สร้างใหม่ ไม่ใช่แก้ทับ)

**ข้อมูลที่แสดง**: 2 ตาราง — รอบันทึก (IMEI/รุ่น/วันที่ปล่อย/ปุ่ม) และยืนยันแล้ว (IMEI/รุ่น/ยอด/วันที่รับเงิน/บันทึกเมื่อ/ปุ่มแก้ไขถ้าเป็น owner)

**edge case/state พิเศษ**:
- ยอด 0 บาท = "ยืนยันว่าไม่มีค่าคอม" ยังคงขึ้นในลิสต์ยืนยันแล้ว แต่**ไม่นับรวมในหน้ารายงาน**
- ทั้งสองลิสต์เป็น empty state ข้อความบอกชัดเจนแยกกัน ("ไม่มีเครื่องที่รอบันทึก" / "ยังไม่มีรายการ")
- **ยังไม่มี mobile card layout แยก** — ใช้ตาราง desktop เดียวกันทุกขนาดจอ (ต่างจากหน้าอื่นที่ทำ responsive ไว้แล้ว — น่าจะเป็นจุดที่ควรทำเพิ่มถ้า staff ใช้มือถือหน้างานจริง)

## รายงาน (`/report`)

**ใครใช้**: owner เท่านั้น
**จุดประสงค์**: ภาพรวมผลประกอบการ ดูกำไร/รายได้ย้อนหลัง ไล่ดูละเอียดถึงระดับบิลได้

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- ปุ่มลัดช่วงเวลา: วันนี้/เดือนนี้/ปีนี้ (ปีนี้จะสลับ grouping เป็นรายเดือนอัตโนมัติ) + custom date range 2 ช่อง
- สลับมุมมองกลุ่ม: รายวัน/รายเดือน/รายปี
- ตารางแบบ **drill-down ซ้อนกัน**: ปี → เดือน → วัน → รายการจริงของวันนั้น (คลิกแถวเพื่อกาง/หุบ)
- เปิดดูรายละเอียดบิลขายแต่ละใบได้ (สินค้า/จำนวน/ราคา/ส่วนลดต่อรายการ) โดยไม่ออกจากตาราง

**ข้อมูลที่แสดง**: การ์ดสรุป 4 ใบ (กำไรสุทธิ/กำไรขาย/กำไรงานซ่อม/ค่าใช้จ่าย), ตารางคอลัมน์เงิน 7 คอลัมน์ (ยอดขาย/กำไรขาย/รายได้ซ่อม/กำไรงานซ่อม/ค่าคอม SF/ค่าใช้จ่าย/กำไรสุทธิ)

**edge case/state พิเศษ**:
- **มือถือซ่อนคอลัมน์รอง** เหลือแค่คอลัมน์ "กำไรสุทธิ" กับชื่อช่วงเวลา — ไม่ใช่ table↔card แบบหน้าอื่น แต่เป็น column-hiding
- ทุกยอดเงินติดลบได้จริง (ไม่ใช่ error) ระบบโชว์เป็นสีแดงเฉยๆ — เดือนที่ไม่มีขายเลยแต่มีรายจ่าย/ตัดสต็อกจะติดลบได้
- ช่วงว่างไม่มีข้อมูลมี empty state ข้อความชัดเจน
- พิมพ์วันที่ครึ่งเดียว (ยังไม่ครบ) จะไม่ค้างที่ "กำลังโหลด" ตลอดไป — มี error state จับไว้

## รายจ่าย & เติมเงินวอลเล็ต (`/expenses`)

**ใครใช้**: owner เท่านั้น
**จุดประสงค์**: บันทึกรายจ่ายร้านแบบเต็ม (ไม่ผูกกับวันปิดร้านวันเดียวเหมือนหน้า close-day) และติดตามยอดเติมเงินวอลเล็ตของแต่ละค่ายมือถือ

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- ฟอร์มเพิ่มรายจ่าย: รายการ, จำนวนเงิน (ขั้นต่ำ 0.01), วันที่ (เลือกวันไหนก็ได้ ไม่ล็อกวันนี้)
- ลบรายจ่ายได้ (มี confirm)
- ฟอร์มเติมเงินวอลเล็ต: เลือกค่าย + จำนวนเงิน

**ข้อมูลที่แสดง**: ตาราง/การ์ดรายจ่ายทั้งหมด + ยอดรวมท้ายตาราง, การ์ดยอดวอลเล็ตแยกตามค่าย 3 ใบ (ยอดเติมสะสม / ยอดใช้ไป / คงเหลือ)

**edge case/state พิเศษ**:
- **responsive: table (desktop) ↔ card (มือถือ)** เหมือนสต็อก/งานซ่อม
- ต่างจาก close-day ตรงที่หน้านี้เป็น "รายจ่ายร้านทั้งหมดไม่จำกัดวัน" ส่วน close-day เป็น "รายจ่ายของวันที่กำลังปิดเท่านั้น" — สอง flow คนละจุดประสงค์แต่ทำเรื่องคล้ายกัน ควรคุยกับ dev ว่าตั้งใจแยกหรือควรรวม UX

## ตั้งค่า (`/settings`)

**ใครใช้**: owner เท่านั้น
**จุดประสงค์**: สำรองข้อมูลระบบทั้งหมดออกเป็นไฟล์ ไว้กู้คืนกรณีฉุกเฉิน (หน้านี้เรียบง่ายมาก ยังไม่มีฟีเจอร์ตั้งค่าอื่น)

**ฟังก์ชัน/ฟีเจอร์หลัก**:
- ปุ่มเดียว "ดาวน์โหลดไฟล์สำรอง" → ดึงข้อมูลทุกตาราง (สินค้า/เครื่อง/บิล SF/ยอดขาย/งานซ่อม/รายจ่าย/วอลเล็ต/ผู้ใช้) เป็นไฟล์ JSON ดาวน์โหลดอัตโนมัติ

**ข้อมูลที่แสดง**: หลังดาวน์โหลดเสร็จ โชว์สรุปจำนวนแถวที่ export ได้ต่อตาราง

**edge case/state พิเศษ**:
- ปุ่มเปลี่ยนข้อความเป็น "กำลังรวบรวมข้อมูล" ระหว่างโหลด (อาจใช้เวลาถ้าข้อมูลเยอะ — ดึงทีละ 1000 แถวต่อตาราง)
- error แสดงข้อความรวม ไม่บอกว่าตารางไหนพัง (แม้ error จริงจะรู้ชื่อตาราง แต่ UI ไม่โชว์ให้ผู้ใช้เห็น)

## สรุป responsive pattern ที่มีอยู่แล้ว

| หน้า | รูปแบบ |
|---|---|
| สต็อก, งานซ่อม, รายจ่าย | desktop table ↔ mobile card แยกไฟล์กันจริง |
| รายงาน | column-hiding (ไม่ใช่ card) |
| หน้าขาย | บล็อกจอแคบไปเลย ไม่มี mobile layout |
| ปิดร้าน, ค่าคอม SF+ | **ยังไม่มี mobile-specific layout** — ค่าคอม SF+ น่าจะเป็นช่องโหว่ เพราะ staff น่าจะเปิดหน้างานจริงบนมือถือบ่อย
